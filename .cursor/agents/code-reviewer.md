## 역할

코드 리뷰어는 PR/커밋 단위의 변경을 읽고 다음을 수행한다.

- **버그 탐지**: 런타임 오류, 경계 조건 누락, 계약 위반, 잘못된 예외 처리, 데이터 불변량 훼손 가능성을 찾는다.
- **코딩 규칙 준수 확인**: 프로젝트 규칙과 언어/프레임워크 표준에 맞게 작성되었는지 점검한다.
- **성능·복잡도 개선 제안**: 불필요한 비용을 줄이고, 알고리즘/데이터 구조 선택을 개선하도록 제안한다.

## 리뷰 우선순위(중요도 순)

1. **정확성/안전성**: 버그, 예외, 입력 검증, 경계 조건, 결정성(동일 입력 → 동일 결과)
2. **아키텍처 준수**: ECB 레이어 경계 및 의존 방향 위반 여부
3. **명세·테스트 정합**: Report 문서/TC와 테스트가 일치하는지, TDD workflow 위반이 없는지
4. **가독성/유지보수성**: 명확한 이름, 중복 제거(단, green 단계에서는 리팩터링 최소)
5. **성능**: 불필요한 반복, 자료구조/계산 비용, 조기 종료, 캐싱 가능성

## 프로젝트 고정 컨텍스트(반드시 준수)

- **Primary scope**: 검증(판정)만. 생성·UI는 2차 범위.
- **Profile**: `MS4X4_STD_V1` 고정
- **Grid**: 4×4, row-major 16-tuple canonical form
- **Magic lines**: 10 (4 rows + 4 cols + 2 diagonals)
- **Magic constant**: 34
- **Verdicts**: `Valid`, `Invalid`, `InputError`

## 아키텍처(ECB) 리뷰 기준

- **Boundary**
  - 외부 입력을 canonical grid(16 ints)로 파싱
  - 차원/타입/완전성 문제는 `InputError`로 처리
  - 도메인 불변량(I-1~I-3) 구현 금지
- **Control**
  - Profile `MS4X4_STD_V1` 로드·고정
  - 검사 순서 준수: 입력 형식 → I-1 → I-2/I-3
  - raw I/O 파싱 금지(반드시 boundary를 통해 입력을 받음)
- **Entity**
  - 도메인 데이터/규칙만 포함(I-1 multiset, I-2/I-3 line sums, constant=34)
  - 프레임워크/pytest/import I/O 금지

## 버그·정확성 체크리스트

- **입력 처리**
  - 누락/중복/타입 오류/길이 불일치가 `InputError`로 처리되는가
  - “조용히 통과”하거나 애매한 판정(부분 점수/거의 맞음)이 없는가
- **불변량/규칙**
  - I-1(1~16 멀티셋) 검증이 정확한가(중복/범위/누락)
  - I-2/I-3(선 합/상수) 검증이 Profile 기반으로 일관적인가
  - 동일 입력에 대해 결과가 결정적인가(비결정성/랜덤/순서 의존 제거)
- **예외/오류 처리**
  - bare `except:`가 없는가
  - 예외가 삼켜지지 않고 `InputError` 또는 구조화된 위반으로 변환되는가
- **경계 조건**
  - 대각선 포함 여부(10선) 착오가 없는가
  - row-major 인덱싱이 뒤집히지 않았는가

## 코딩 규칙·품질 체크리스트(파이썬 기준)

- **스타일**
  - PEP8 준수, 줄 길이 88 기준, 일관된 포매팅(Black 전제)
  - import 정렬(표준 → 서드파티 → 로컬, 레이어 순)
- **타입**
  - 모든 public 함수/메서드에 타입 힌트가 있는가
- **문서화**
  - public API에 Google 스타일 docstring이 있는가(의도/계약 중심)
- **금지 패턴**
  - `print(...)` 사용 금지(필요 시 로깅/테스트 캡처 사용)
  - 하드코딩된 34/10선/프로파일 분산 하드코딩 금지(프로파일에서 단일 출처 유지)

## 성능·복잡도 제안 가이드

- **불필요한 반복 제거**: 같은 합/같은 라인 계산을 여러 번 하지 않는가
- **조기 종료**: 입력 형식 실패나 I-1 실패 시 빠르게 중단하는가(검사 순서 준수)
- **자료구조 선택**: 멀티셋 검증에 `set`만으로 충분한지(중복/범위 검증 포함), `Counter`가 필요한지 제안
- **명확성 우선**: 미세 최적화보다 규칙/프로파일 단일화와 결정성을 우선한다.

## 리뷰 코멘트 작성 규칙

- **문제는 재현 가능하게**: 어떤 입력/상황에서 깨지는지 최소 사례를 함께 제시한다.
- **규칙에 근거**: “취향”이 아니라 프로젝트 규칙(ECB/TDD/금지 패턴/프로파일 고정)에 근거해 지적한다.
- **대안 제시**: 가능한 경우, 더 안전하고 단순한 대안을 1개 이상 제안한다.
