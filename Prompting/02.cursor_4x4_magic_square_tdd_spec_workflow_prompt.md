`MagicSquare_XX`는 이미 **main(안정)** + **develop(통합)** 구조이고, 구현은 아직 없으며 README도 **판정(검증) 우선·역할 분리·TDD**를 전제로 하고 있습니다. Red–Green–Refactor에 맞춘 브랜치 전략을 정리합니다.

## 핵심 원칙: Red/Green/Refactor ≠ 브랜치

| 단계 | 권장 단위 | 이유 |
|------|-----------|------|
| Red / Green / Refactor | **커밋**(또는 로컬 작업) | 브랜치마다 나누면 merge 비용만 커지고, “한 기능 = 한 PR” 추적이 어려움 |
| 기능 단위(판정 규칙·시나리오 슬라이스) | **feature 브랜치** | 리뷰·롤백·이력이 명확함 |

즉, **브랜치는 “무엇을 만드는가”**, **커밋은 “TDD 사이클”**에 맞추는 편이 좋습니다.

## 권장 브랜치 모델

```text
main          ← 문서·릴리스 스냅샷, CI 통과한 결과만
  ↑ merge (PR)
develop       ← 통합·항상 빌드 가능
  ↑ merge (PR)
feature/*     ← TDD로 한 덩어리씩 구현
spike/*       ← (선택) 격자 표현·라이브러리 등 탐색만
```

## feature 브랜치 쪼개기 (Invariant 순)

| 순서 | 브랜치 예시 | Red 단계에서 고정할 것 |
|------|-------------|------------------------|
| 0 | `feature/scaffold-tests` | 테스트 러너, 격자 표현, 판정 결과 타입 |
| 1 | `feature/validate-lines-definition` | 마법 선 정의 (**I-4**) |
| 2 | `feature/validate-i1-unique-1-16` | 1~16 각 1회 (**I-1**) |
| 3 | `feature/validate-i2-magic-constant` | 선 합·상수 34 (**I-2, I-3**) |
| 4 | `feature/validate-orchestrator` | 동일 입력 → 동일 판정 (**I-5**) |
| 5 | `feature/validate-invalid-input` | 잘못된 입력 (**I-7**) |
| 6 | (2차) `feature/validate-partial` | 부분 배치 (**I-8**) |
| 7 | (선택) `feature/generate-complete` | 생성 (**I-6**) |

## 피하는 패턴

| 패턴 | 문제 |
|------|------|
| `red/...`, `green/...` 브랜치 3개/기능 | merge 3번, 중간 상태 추적 어려움 |
| `develop`에 Red만 push | CI 기본선 깨짐 |
| 한 브랜치에 I-1~I-7 전부 | PR 거대 |

## Red / Green / Refactor 브랜치 전략 — 검토

**결론: 학습·회고 목적이면 진행해도 됩니다.** `spec`을 먼저 두는 순서는 README의 “명세 → TDD”와 잘 맞습니다.

| 관점 | 의견 |
|------|------|
| **장점** | 단계가 Git에 남아 Red/Green/Refactor가 분명함 |
| **단점** | 기능마다 merge 3번, Refactor 브랜치가 Green과 어긋날 수 있음 |
| **실무** | feature 하나 + 커밋(`test:`/`feat:`/`refactor:`)이 일반적 |

**권장 흐름:**

```text
develop
  └── spec          ← 계약·시나리오·비목표
        └── red     ← 실패 테스트만
              └── green
                    └── refactor → develop merge
```

- 슬라이스마다 `red → green → refactor` 한 바퀴 후 **refactor 완료 시에만** `develop` merge
- `red` 단독 merge 금지
