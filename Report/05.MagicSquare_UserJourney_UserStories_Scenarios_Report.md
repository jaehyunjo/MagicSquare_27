## 0. Executive Summary

본 문서는 Magic Square 4×4 TDD Practice의 **Epic → Journey → Story → Scenario** 연결을 Level 1~5 형식으로 정리하고, **불변식/계약 기반 추적성**과 **Boundary/Domain 분리**가 유지되는지를 점검한 결과를 담는다.

핵심 결론은 다음과 같다.

- Journey와 Story는 **계약(입력/출력/오류) 우선** 및 **책임 분리(Blank/Missing/Validator/Solver)** 구조로 일관성이 높다.
- Technical Scenario는 Boundary 입력 검증(일부)과 Solver reverse 성공 케이스는 확보했으나, **Story 2~4 시나리오**, **small-first 성공**, **4×4 형태 오류** 등이 누락되어 Level 4 보강이 필요하다.

## 2. Fixed Domain Rules / Contracts (학습 과제 규칙)

### 2.1 Input Contract (Boundary)

- 입력은 **4×4 int 행렬**
- 0은 **빈칸**
- 빈칸(0)은 **정확히 2개**
- 값은 **0 또는 1..16**
- **0을 제외한 중복 숫자 금지**

### 2.2 Output Contract (System)

- 출력은 **int[6]**
- 좌표는 **1-index**
- 출력 형식은 **[r1, c1, n1, r2, c2, n2]**

### 2.3 Domain Invariants (Logic)

- 마방진 상수는 **34**
- 완성 그리드는 모든 **행/열/대각선** 합이 **34**
- Solver는 **small-first** 조합 시도 후 실패 시 **reverse** 조합을 시도

## 3. Level 2: User Journey (5 stages) — Snapshot

| Stage | 핵심 목적 | 핵심 산출물(후속 분해 포인트) |
|------|----------|------------------------------|
| Stage 1 Problem Recognition | “정답 구현”이 아닌 “불변식 기반 설계 훈련”으로 재인식 | 불변식 후보(I-A~I-E) 및 계약 우선순위 |

| Stage 5 Regression Protection | 정상/오류/조합 실패/형식 케이스로 회귀 방지 | 보호 대상(계약/불변식)별 케이스 목록 |

## 8. Next Step (문서 단계 후속)

본 문서는 Task로 분해하지 않는다. 다만 다음 단계에서 빠르게 `red → green → refactor`로 진입할 수 있도록, Level 4를 다음 순서로 보강하는 것을 권장한다.

1. **Boundary**: 4×4 형태 오류 시나리오(입력 계약 완결)
2. **Domain**: BlankFinder/MissingNumberFinder/Validator 단독 시나리오(책임 분리의 실증)
3. **Control/Solver**: small-first 성공 / both-fail 시나리오(정상+실패 계약 고정)
