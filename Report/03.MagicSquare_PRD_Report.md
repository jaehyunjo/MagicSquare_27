## 0. Executive Summary

MagicSquare_XX는 4×4 마방진을 **생성하는 알고리즘**이 아니라, **판정 기준을 고정하고 임의의 배치에 일관되게 적용·반복·기록**하는 학습·실험 제품이다.

1차 범위는 **검증(판정)만** 다룬다. 완전 배치 4×4 격자에 대해 `Valid` / `Invalid` / `InputError` 판정과 구조화된 위반 정보를 반환한다. 성공 기준은 "한 격자를 맞춘다"가 아니라 **동일 입력·동일 기준 → 동일 판정(I-5)**, 실패 시 **명시적 사유(I-7)** 이다.

본 PRD는 구현(`red`/`green`/`refactor`) 전에 제품의 목적, 범위, 계약, 아키텍처 제약, 검증 기준을 고정한다.

## 1. Vision & Product Intent

### 1.1 Vision

> **제약이 있는 유한 상태(4×4 배치)에 대해, 고정된 규칙으로 참·거짓을 말하고, 그 말이 바뀌지 않도록 경계와 불변량을 스스로 명확히 하는 사고를 훈련한다.**

### 1.2 Product Intent

| 구분 | 내용 |
|------|------|
| **표면 목표** | 4×4 격자에 1~16을 배치해 행·열·대각의 합을 맞추는 것처럼 보이는 문제 |
| **실제 목표** | "마방진" **판정 기준**을 고정하고, 임의의 배치에 그 기준을 **일관되게 적용·반복** |
| **훈련 방향** | 명세화, 불변량, 경계·계약, 역할 분리, Dual-Track TDD 기반 검증 우선 사고 |

알고리즘 난이도보다 **불변식 기반 사고, 계약 기반 테스트, Dual-Track UI + Logic TDD, 리팩토링 훈련**이 핵심 가치이다.

## 2. Background

### 2.1 상황

4×4 격자에 1~16을 배치했을 때, 행·열·대각선 등 여러 "줄"의 합이 동일한지를 다루는 상황이다. "무언가를 만든다"기보다:

- 규칙이 있는 배치가 존재하는지
- 그 규칙을 만족하는 배치를 어떻게 **검증**하는지
- 그 결과를 어떻게 **확인·활용**하는지

를 다루는 **불확실성·제약·검증** 문제이다.

### 2.2 왜 프로그램인가

| 관점 | 프로그램이 필요한 이유 |
|------|------------------------|
| **반복 가능성** | 동일 입력 → 동일 절차 → 동일 결과 |
| **검증 자동화** | 정의된 모든 마법 선을 누락 없이 검사 |
| **오류 방지** | 산술·규칙·절차 오류를 기계적으로 차단 |
| **규칙 외화** | 제약을 명세 가능한 형태로 다루는 연습 |

### 2.3 왜 TDD인가

4×4 마방진은 **수학적 불변량이 분명**하고 **입출력이 격자로 고정**되어 TDD와 잘 맞는다. TDD는 "먼저 돌아가는 것"이 아니라 **"먼저 고정되는 의미(명세)"**를 두는 설계 방식이다.

## 3. Problem Definition

### 3.1 잘못된 정의 (피할 표현)

> 4×4 격자에 1~16을 넣어 행·열·대각 합이 같게 만드는 프로그램을 만든다.

— 산출물·완성에만 묶이고, 판정·반복·역할 분리가 빠진다.

### 3.2 정확한 정의

> 4×4 격자에 대한 **"마방진" 판정 기준을 먼저 고정**하고,  
> 임의의 배치(완전·부분·잘못된 입력 포함)에 대해 그 기준을 **일관되게 적용·반복·기록**할 수 있는지를 다루는 문제.  
> 완전한 배치를 얻는 것은, 필요 시 **판정 기준을 만족하는 산출물을 확보**하는 행위로만 한정한다.

### 3.3 Why Chain 요약

```text
STEP 1  관찰      → 제약·검증·맥락; "만든다"가 아닌 상황 서술
STEP 2  Why #1    → "완성" 가정과 생성/검증·부분 상태 긴장
STEP 3  Why #2    → 프로그램 = 반복·자동 검증·오류 방지·규칙 외화
STEP 4  Why #3    → TDD = 통제·불변량·명확한 입출력 계약
STEP 5  정의      → 판정 기준 중심의 진짜 문제 + I-1~I-8 + 사고 능력
```

| **출력** | `Valid` \| `Invalid` \| `InputError` + 구조화된 위반 목록 |

| **표현** | 최소 입력 어댑터 계약 (격자 → 내부 모델 변환) |

- 마방진 **생성 알고리즘**

- 성능·최적화 벤치마크
- **부분 판정**·"거의 맞음" 점수화

## 8. Functional Requirements

### 8.1 Input Contract

| 조건 | 처리 | 판정 | 사유 코드 |
|------|------|------|-----------|
| 행·열이 4×4가 아님 | 거부 | `InputError` | `INPUT_DIMENSION_MISMATCH` |
| 16칸 미만·빈 칸·null | 거부 | `InputError` | `INCOMPLETE_GRID` |
| 비정수·NaN | 거부 | `InputError` | `INPUT_NON_INTEGER` |
| 16칸 모두 정수, 값 일부가 1~16 밖 | 규칙 위반 | `Invalid` | `I1_VALUE_OUT_OF_RANGE` |
| 1~16 각각 정확히 1회 아님 | 규칙 위반 | `Invalid` | `I1_DUPLICATE` / `I1_MISSING` |
| I-1~I-2 모두 통과 | 수용 | `Valid` | (위반 목록 빈) |

**격자 표현 (권장):** row-major 16튜플 `(v0,…,v15)` — `v_{4r+c}` = 행 `r`, 열 `c`

**정책:** 구조·형식 오류는 `InputError`, 채워진 완전 격자에서 도메인·합 실패는 `Invalid`. "거의 맞음" → `Valid` 금지 (I-7).

### 8.2 Output Contract

```text
VerdictResult {
  verdict: Valid | Invalid | InputError
  violations: Violation[]
  magicConstantExpected: 34
  profileId: "MS4X4_STD_V1"
}
```

```text
Violation {
  code: string           // 예: I2_LINE_SUM_MISMATCH
  invariantId: I-1 | I-2 | …
  lineId?: string        // 예: R2, C0, D_MAIN
  expected?: number
  actual?: number
  detail?: string
}
```

### 8.3 Domain Profile

| 항목 | 값 |
|------|-----|
| **Profile ID** | `MS4X4_STD_V1` |
| **Magic Constant** | `34` |
| **Magic Lines** | 10 (행 4 + 열 4 + 주대각 1 + 반대각 1) |

| lineId | 유형 | 셀 (row, col) 0-based |
|--------|------|------------------------|
| `R0`~`R3` | 행 | 행 `r`의 `(r,0)~(r,3)` |
| `C0`~`C3` | 열 | 열 `c`의 `(0,c)~(3,c)` |
| `D_MAIN` | 주대각 | `(0,0),(1,1),(2,2),(3,3)` |
| `D_ANTI` | 반대각 | `(0,3),(1,2),(2,1),(3,0)` |

### 8.4 Invariants

| ID | 불변 조건 | 1차 | 위반 시 |
|----|-----------|-----|---------|
| **I-1** | 1~16 각 정확히 한 번 | ✅ | `Invalid` |
| **I-2** | 모든 마법 선 합 = 34 | ✅ | `Invalid` |
| **I-3** | 마법 상수 = 34 (논리적 결정) | ✅ | 기대값 불일치 |
| **I-4** | 판정 규칙 집합 동일 | ✅ | Profile 불일치 |
| **I-5** | 동일 입력 → 동일 판정 | ✅ | 결정성 위반 |
| **I-6** | 생성 결과는 I-1~I-3 만족 | 2차 | — |
| **I-7** | 잘못된 입력은 조용히 "거의 맞음" 처리 안 됨 | ✅ | `InputError`/`Invalid` + violations |
| **I-8** | 부분 배치 규칙 사전 정의·일관 | 2차 | — |

**우선순위:** `I-4 → I-1~I-3 → I-5, I-7 → I-6(2차) → I-8(2차)`

### 8.5 검사 순서 (Control)

```text
입력 형식·차원·완전성 (I-7) → I-1 → I-2/I-3 (I-4 선 목록 사용)
```

## 9. Architecture & Design Constraints

### 9.1 Clean Architecture + ECB

```text
┌─────────────────────────────────────────────────────────────────┐
│ [Boundary]  외부 입출력 (파싱, 직렬화)                            │
└────────────────────────────┬────────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│ [Control]   오케스트레이터 (Profile 로드, 검사 순서, VerdictResult) │
└──────┬──────────────┬──────────────┬────────────────────────────┘
       ▼              ▼              ▼
┌────────────┐ ┌────────────┐ ┌────────────────────┐
│ I-4 선     │ │ I-1 집합   │ │ I-2/I-3 선 합      │
│ 레지스트리 │ │ 규칙       │ │ 규칙               │
└────────────┘ └────────────┘ └────────────────────┘
       [Entity Layer]
```

### 9.2 Layer Responsibilities

| Layer | Responsibilities | Must Not |
|-------|------------------|----------|
| **Boundary** | 외부 형식 → CanonicalGrid, 차원·타입·완전성 → InputError, VerdictResult 직렬화 | I-1~I-3 도메인 규칙, 생성 알고리즘 |
| **Control** | Profile `MS4X4_STD_V1` 로드·고정, 검사 순서 강제, VerdictResult 조립 | Boundary 세부 의존, raw 입력 직접 처리 |
| **Entity** | Grid, Verdict, Violation, MagicLine, Profile, I-1/I-2/I-3 규칙 | pytest, I/O, UI/CLI, frameworks |

### 9.3 Dependency Direction

| Allowed | Forbidden |
|---------|-----------|
| `boundary → control` | `entity → control` |
| `control → entity` | `entity → boundary` |
| `boundary → entity` (DTO/enum only) | `control → boundary` |

## 10. Development Method (Dual-Track TDD)

### 10.1 Workflow

```text
develop → spec → red → green → refactor → develop
```

| Phase | Branch | Description |
|-------|--------|-------------|
| **spec** | `spec` | 설계·계약·TC 명세 고정. `src/` 프로덕션 코드 없음 |
| **red** | `red` | 실패 테스트 먼저 작성, pytest로 실패 확인 |
| **green** | `green` | 최소 구현으로 TC 통과 |
| **refactor** | `refactor` | 동작 동일, 구조 개선 |

### 10.2 Vertical Slices

| Slice | 목표 | TC |
|-------|------|-----|
| **S0** | 스캐폴드·계약 스텁 | TC-008, TC-011 |
| **S1** | I-4 마법 선 고정 | TC-014 준비 |
| **S2** | I-1 숫자 집합 | TC-004~006 |
| **S3** | I-2, I-3 선 합 | TC-001~003, TC-007, TC-013~015 |
| **S4** | I-5, I-7 오케스트레이터 | TC-001~017 |
| **S5** | (2차) I-6 생성 | — |
| **S6** | (2차) I-8 부분 | TC-018 |

### 10.3 Commit Prefix

| 접두사 | 용도 |
|--------|------|
| `docs:` | spec 문서·TC 명세 변경 |
| `test:` | red — 실패 테스트 추가 |
| `feat:` | green — Slice 동작 구현 |
| `refactor:` | refactor — 동작 동일 구조 개선 |

## 11. Quality Requirements

### 11.1 Testing

| 항목 | 기준 |
|------|------|
| **Framework** | pytest |
| **Pattern** | AAA (Arrange/Act/Assert) |
| **Naming** | `test_<tc_id>_<intent>` (예: `test_tc001_durer_valid`) |
| **Coverage** | line coverage ≥ 80% (TC 누락 대체 불가) |
| **TC Range** | TC-001 ~ TC-017 (1차) |

### 11.2 Prohibited Patterns

| 금지 | 대안 |
|------|------|
| `print(...)` | `logging.getLogger(__name__)` 또는 pytest `caplog` |
| Bare `except:` | `except SpecificError as e:` → InputError/Violation 변환 |
| 하드코딩된 34/10선 | Profile `MS4X4_STD_V1` + MagicLineRegistry |
| `@pytest.mark.skip`, `xfail` | 명세 또는 구현 수정 |
| `Valid \| 거의 맞음 \| 부분 점수` | `Invalid` + 구조화 violations |
| Entity에서 I/O | Boundary 레이어 어댑터 |
| RED 없이 src/ 기능 추가 | red → green 순서 준수 |
